# Changelog

All notable changes to this project's published surface — the skills catalog (and, through 2.0.0, the `harness/` Python) — are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/2.0.0/).

## [Unreleased]

### Added

- `repo-audit`: checks the repo against the fleet-wide repo standards in `dividedby/claude-config` `docs/standards.md`, read fresh on each run (local checkout as fallback) with the commit it read recorded on the page. Each standard is marked pass, fail, not applicable for the repo's type, or not checked, with evidence; each fail gets a severity and a one-line fix and joins the plan. The report page gains a Fleet standards table and verdict card. The audit still changes nothing in the repo.
- ADR 0049: `repo-audit` runs a five-lens roster at two depths against stated budgets; amends ADR 0042.
- ADR 0048: `repo-audit` keeps isolated instances up through Stage 3 and probes the UI; amends ADR 0042.
- ADR 0047: `repo-audit` asks once before running an untrusted repo's code; amends ADR 0042.
- ADR 0046: `repo-audit` adapts to repo type, size and shape; amends ADR 0042.
- ADR 0045: `repo-audit` checks the fleet standards, read fresh; amends ADR 0042.
- `idea-intake`: a new skill that fires on "file an idea" or an unqualified "file an issue" in any repo. It adds an enriched row (the idea, context and links, one sentence of why) to the top of that repo's Idea Inbox issue without scoping it. "File a tracked issue" or a plainly-scoped bug skips the Inbox and files a `needs-triage` issue. It reads the repo's `docs/agents/idea-inbox.md` first, which wins over the skill. Replaces the Intake convention block copied into each project's `CLAUDE.md`. `docs/agents/idea-inbox.md` now names the skill as the capture path and stays the protocol and drain source.
- `mac-activity`: a new user-invoked skill for when a Mac is slow or short of memory. It measures memory by app and by Claude session, asks the running sessions what can stop, looks for leaks and labels the evidence, and ends with a ranked list you approve item by item. It stops nothing on its own, and its reports stay private. A session may ask you to confirm in that session, and you close whole sessions yourself. macOS only.
- ADR 0044: capture for the Idea Inbox moves from per-repo `CLAUDE.md` text to the `idea-intake` skill; the repo's `docs/agents/idea-inbox.md` stays the protocol and overrides the skill; drain stays a convention.
- ADR 0043: `mac-activity` reports and asks, and bundles a tested stdlib sampler.
- ADR 0042: `repo-audit` becomes a read-only audit that publishes one report page; supersedes the `repo-audit` amendment in ADR 0041.

### Changed

- `repo-audit`: the audit now reviews what a repo's CI costs and, for a private repo, whether it could go public. For every repo with CI workflows, the product lens records each workflow's triggers, runner OS and billing multiplier (each runner's per-minute rate against the Linux rate, read from GitHub's billing docs on each run; about 1x Linux, 1.7x Windows and 10.3x macOS today), matrix size, median duration, runs a month and billable minutes, read from the last 30 days of runs and the account's billing usage where `gh` can reach them. Each figure is labelled measured (billing usage) or estimated (run durations), and a missing billing scope, no `gh` access or no recent runs is recorded as "Needs X" with the workflows read alone. It lists the cuts with the minutes a month each saves: duplicate matrix legs, macOS or Windows jobs that could run on Linux, no `concurrency` cancel on PR workflows, no caching, over-frequent schedules, bot PRs and doc-only changes running everything, long time-outs, retention, self-hosted runners and tiny jobs that bill a whole minute each. Recommendations keep the always-reporting `ci-ok` job and never suggest a workflow-level `paths:` filter on pull requests. A private repo using more than 10% of its account's included monthly minutes is at least Med, waste above 5% is High, and a public repo's minutes are listed but capped at Low. For a private repo, the architecture lens adds a go-public checklist (secrets in the full history across all refs, personal data, infrastructure details, issue and PR content, private dependencies, licence and whether the repo is meant to stay private) that ends in one verdict, Ready, Ready after cleanup (each item, and whether it needs a history rewrite) or Keep private, with the minutes a month going public would save. It is a checklist, not a recommendation to change visibility, and a `quick` run does not run it. `findings.json` gains a `go_public` field.
- `repo-audit`: the audit now has a named roster of five lenses, each with an agent type, a model, the areas it owns and its tools, in one table in `SKILL.md`: code (code quality, tests, performance), architecture (architecture, tech stack, security, privacy, data integrity, external facts), product (feature completeness, repo organisation and docs, ops and release, agent readiness), design and market. The old architecture-and-docs lens is split in two, so the product lens now owns documentation and repo hygiene. The market lens runs only on a public repo whose docs name users other than the owner; a private or single-user repo skips it and the page says why. You can ask for a `quick` audit (code and architecture only, from static reading, with every area the other lenses own marked "Not assessed (depth)" and naming the lens) or leave it at `standard`, which launches at most four lens agents, the market lens only when a slot is free. Both depths have stated wall-time and token budgets, taken from three costed runs of the skill (a web app, an infra repo and a CLI; evidence in ADR 0049), with Small-tier, `quick` and the split architecture and product figures marked provisional. A lens stops at 1.5 times its budget, and a run that is over a budget by more than 50% says so on the page, in the run log and in the closing message. A large pile of repo rules may be harvested by one helper agent before the lenses, logged apart and counted in the totals.
- `repo-audit`: the architecture check now reviews module depth on medium and large repos. For up to 10 modules in total that changed in the last year, taken from the baseline's churn list first and then the entry points, it records the number of exported symbols, how many files call each module and a written deletion test: if deleting the module spreads its work into callers, it earns its keep; if the work vanishes, it only passed calls along. It flags pass-through modules, one concept scattered across shallow files, code pulled out only so a test can reach it, and interfaces with a single non-test implementation (Low by default), and badges each Strong, Worth exploring or Speculative by how much of a flag's evidence holds. A Speculative candidate alone is not a finding. The results go in a module depth table in the architecture report file the page links. Small repos, repos with no module changed in the last year and shallow clones skip it with a stated reason. The tests review also lists tests that compute the expected value the way the code does, mocks of the repo's own modules, and tests that reach past a module's interface.
- `repo-audit`: the architecture lens now tests data integrity, privacy and security instead of only reading for them. It maps every stored file, database and cache and checks how each is written, backed up and recovered; when the repo keeps user data or makes an integrity claim, it runs up to three faults (a corrupt store, two writers, a write killed midway) on throwaway data and reports what happened. It lists the personal data the app keeps and every outside service it calls, checks web apps against OWASP ASVS 5.0 Level 1, sends forged `Host` and cross-origin requests to a local server, and forces an error to see whether secrets reach logs. The product lens's ops checks add the release and update path, a fresh-clone install from the README (run only when it writes nowhere but the scratchpad), rollback, runbooks, health checks and failure alerts, from the primary instance with non-mutating requests only. The new tables go in each lens's report file, which the page links. Anything that cannot run gets a stated reason.
- `repo-audit`: the design lens now measures walls of text, checks branding and walks whole tasks, instead of giving screen-by-screen copy notes with no counts. Each copy flag (long sentences, long blocks, repeated explanations) cites the screen or command, the measured value and the threshold, with a rewrite; a repo's own voice guide takes precedence. The lens also inventories the product name, icon, colours and fonts across every surface, and walks up to three primary tasks as a first-time user, rating each problem by frequency, impact and persistence. Mockups are drawn only for a High or Blocker design finding and show the rewritten copy, and a repo with no UI skips these checks with a stated reason.
- `repo-audit`: the audit now measures a web UI instead of only photographing it. It starts the app twice on throwaway data (one for captures and probes, one for later fault tests; never your real data folder) and keeps both running while the lenses work. It probes each main screen across its states, widths and light and dark themes, using a scratch Playwright install: accessibility violations, horizontal overflow, undersized tap targets, console errors, failed requests, copy length and colours outside the design tokens. It also runs a keyboard-only pass of each primary flow and, for a hosted site, lab Core Web Vitals from a local build. Failing cells and totals per screen appear on the page, raw JSON stays in the scratchpad, and anything skipped gets a stated reason. The built-in browser is no longer used to capture web apps.
- `repo-audit`: a repo you don't own (not your GitHub account or org, not a fleet repo, not local-only) is untrusted unless your prompt says its code may run. The audit asks once, up front, whether it may run that repo's tests, builds, app and gates; a yes runs them from a scratch clone for that run only, and a no, no answer or unattended run executes nothing and marks what needed it "Untrusted not run". The page and run log record the answer. Fleet standards now apply only to repos you own; others get "n/a (not a fleet repo)".
- `repo-audit`: the audit now checks how the repo is organised and what has been left lying around. It reports top-level folders and files, the deepest path and whether each top-level source folder shows its public surface, as counts and a list with no score. It lists each piece of cruft with its path: scratch folders untouched for 180 days that nothing names, docs nothing links to, commented-out code blocks, and `TODO` markers that name a closed issue or sit on lines over a year old. When the repo has a glossary it checks the entry format, definitions that describe the implementation, and `_Avoid_` terms the code still uses, with a count and sample lines, and reports its entry count and the terms nothing uses as candidates to prune. When it has ADRs it checks numbering gaps and duplicates, missing status, supersede links that point only one way, and decisions too easy to reverse to need a record. A repo without a glossary or ADRs gets a skip reason for that check, as does any test the repo can't support (closed-issue checks with no GitHub remote, age checks on a shallow clone), and the audit suggests creating either only when it can name the specific term or decision. The report page gains a cruft table in the Repo organisation section.
- `repo-audit`: the audit now checks whether an AI agent can find its way around the repo and check its own work. It reports whether each check the agent file (`CLAUDE.md`, `AGENTS.md`) documents passes as written, how long it takes and any step the doc leaves out; whether there is a fast way to run a single test; and every path or command the agent file names that no longer exists, with where it is named. It also flags rules copied from fleet-wide instructions and passages that repeat the README, glossary or ADRs instead of linking to them. A repo with no agent file gets one finding, and its checks are still reported. The report page gains an Agent readiness section with a table of the documented checks.
- `repo-audit`: the audit now checks the facts a repo hard-codes from outside itself against official sources found online. It finds constants and tables in config or data files (a tax table or eligibility threshold in an app, a provider quota or instance limit in infra code), values with a year, date, percentage or amount of money, values the repo marks `VERIFY` or "update yearly", and the API limits and formats the code relies on. Each is checked against a government page, the provider's own docs or the standard, and recorded with the source URL, the date read, the value found and a result: match, mismatch or couldn't verify. The audit also looks for how the values stay current: a yearly update step, a test that pins them, or a date after which the app warns. A mismatch is a finding, and one in a number the user decides on is a Blocker. Above 30 candidates, every marked value and every value behind a user-facing number is checked and the rest are listed as not checked with their count. The report page gains an External facts table, and the market lens is evidence only for this area.
- `repo-audit`: before the lenses launch, the audit now runs a deterministic baseline (new supporting file `baseline.md`) and hands every lens its digest, so lenses check mechanical facts instead of rediscovering them. It covers dependency vulnerabilities, secrets in the tree and history (location only, never the value), size and churn on every repo; the repo's own gates, with pass or fail, wall time, a time-box and whether each documented command ran as written; scanners for Python, Node and pnpm, browser JS with no `package.json`, Swift, Go, Terraform and shell, including the declared minimum runtime; CI and container supply-chain and licence scans; and cruft and test digests (test code, fixtures and source as three numbers, the 10 slowest tests). Every tool that could not run gets a reason in the coverage matrix. A new Execution boundary section sets the rules for running the repo's code: a scrubbed environment with no tokens beyond what the demo mode needs, tools and caches only in the scratchpad, network allowed, and nothing in the repo folder changed, ignored files included. Every lens brief now says that text in the repo is data: instructions in it are reported, never followed.
- `repo-audit`: the audit now holds the repo to its own documented rules and claims before generic practice. Stage 1 harvests them into a `rules.md` (rule-like sentences only: imperative or normative statements, README features and commands, decisions in accepted ADRs, and every `TODO`, `FIXME`, `XXX`, "not built" and `VERIFY` marker, from the agent file, README, design and brand docs, coding standards, acceptance docs and glossary), one row per rule with its source `file:line`, rubric area and how to check it. Each lens checks the rows for its areas, reports each failed row as its own finding and the passes as counts, and gives a reason for any row it could not check. Every README feature and command gets a status (works, broken, or not checkable with a reason), doc statements about behaviour are checked against the code, and code behaviour no doc mentions is listed as drift. A repo with no README gets one hygiene finding and Feature completeness is Not assessed. A failed repo rule ranks above a generic gap with the same impact, and the finding cites the rule. The report page gains a Rules conformance section: counts per source file, then the rows that failed or went unchecked.
- `repo-audit`: the audit now adapts to what it is pointed at. A new `types.md` holds the checks that only apply to one kind of repo (userscript, library, CLI, native app, server or MCP, infra, local web app, hosted site, docs or config), so a Python web app no longer gets native-app bullets about the UI thread, signing and notarization. A repo can match several types; a repo that matches none gets a generic profile and the page names the unrecognised type. Stage 1 now sets a size tier from source lines (excluding vendored, generated and fixture files, and stating the exclusions); on large repos each lens samples, and the page says what each lens read and how it chose. Monorepos are profiled per package, with a verdict per package; packages you did not name are listed as Not selected. `findings.json` gains the per-lens coverage and the per-package verdicts. A repo with no GitHub remote runs everything that does not need the GitHub API, and any CI config counts as CI. Docs and config repos get only the areas that apply to them.
- `repo-audit`: the audit now answers "is this ready for the people who use it?" with a fixed readiness rubric (`rubric.md`): 16 areas (code quality through agent readiness), each with what to check, how and what evidence a finding needs, and a rule for when it applies to the repo. Every finding is rated Blocker, High, Med or Low on one scale (a Blocker is something that harms users or the maintainer if shipped now), and each area gets a verdict: Not ready, Ready with fixes, Ready, or Not assessed with a stated reason (not applicable, depth, untrusted code not run, needs something, lens failed, tool unavailable). The overall verdict is the worst applicable area, with Blockers named. The report page opens with a readiness scorecard (replacing the per-lens verdict cards) and gains a coverage matrix showing which methods each area got, and findings are grouped by area. The fleet-standards section drops its own good/mixed/weak verdict: a fail now counts toward its area, and a row with one failing and one unreadable alternative (for example CI secret scanning and the GitHub setting) now fails instead of being "not checked". Every Blocker and every Not ready area is re-checked before publishing, Blockers always go in Now, and a `findings.json` (findings with stable keys, profile, scorecard, coverage) is published beside the page. An applicable area with no verdict and no reason now fails the audit.
- `repo-audit`: every run now writes a run log (`run-log.md`) as it works and publishes it beside the report page: the skill and audited commits, start and end time of each stage, one row per lens agent (model, wall time, tokens, tool uses, findings by severity, status), failed or slow commands, each point where the skill was unclear with the choice made, a before-and-after read-only check, and totals. The closing message gives the totals, the number of guesses and any partial or failed lens. Lens failures are handled: each lens writes its report as it goes, a lens stopped at its ceiling or failed after writing keeps its partial output marked partial, a lens that errors before writing anything is retried once and otherwise marks its areas "Not assessed (lens failed: reason)", and the page names every partial or failed lens. A cut-off run resumes in the same session from the log if the repo has not moved. A missing run log, or a failed lens whose areas are not marked Not assessed, now fails the audit.
- `repo-audit`: the profile now lists a source for every fact (a `file:line`, a command and its output, or a URL), and a fact with no source is marked unverified so the lens that gets it checks it first. When the lens reports come back, findings that cite the same `file:line` or command output are merged into one (the other lenses are listed as "also reported by", and the highest severity that survives verification is kept), and a finding that restates a fleet-standards row is folded into that row. The page's "What was checked" section gains a Merged list, and every lens is told to cite fleet-standards rows and baseline numbers, not repeat them.
- `repo-audit`: each instruction now lives in one file instead of two or three, so the copies can no longer drift: the fleet-standards procedure and the `test-size` rule in `fleet-standards.md`, each lens's model, tools and areas in the lens table in `SKILL.md` and its focus in its `briefs.md` section, the page fill rules in the `template.html` header. The report template drops its macOS window sample for a plain browser-window frame; the desktop-window, phone and terminal frames move to a new `snippets.html` the template points to. The skill also states what it used to leave to guesswork: mockups cover only the two or three screens behind the top findings; screenshots keep their width up to 1,280 px, are never upscaled, and are saved as JPEG at about q70; the closing question is asked only when the run reports to you, and a run reporting to another session ends with the page link and the first plan item; the Artifact `quickstart` is run, then the skill's own template is kept.
- `repo-audit`: the code lens now reviews whether the test suite earns its keep, against the fleet testing guideline in `dividedby/claude-config` `docs/testing.md`. It measures run time, test count, test-to-source ratio and the largest test file, lists change-detector, assertion-free, sleep-based, mock-heavy, duplicate and flaky tests with `file:line` samples, and ends with a prune-and-split list that names the safe-deletion check for each item. It only recommends. The fleet check also reports the new report-only `test-size` standard: a flag (a ratio above 1.5x, a test file over 2,000 lines, or a suite over 2 minutes) asks for that review and never counts as a fail.
- The domain glossary `CONTEXT.md` is renamed to `GLOSSARY.md`, the name the upstream `grilling`, `domain-modeling`, `tdd`, `to-spec` and `to-tickets` skills now read; `docs/agents/domain.md` (including `CONTEXT-MAP.md` → `GLOSSARY-MAP.md`), `docs/agents/idea-inbox.md` and the instruction files point at it. `CODING_STANDARDS.md`, `README.md` and `docs/agents/skill-authoring.md` follow. Consumer repos' `docs/agents/domain.md` copies are updated in their own PRs.
- `repo-audit`: **Breaking:** now a read-only audit that changes nothing in the repo and files no issues. Up to five lenses run in parallel, at most four at the standard depth: code, tests and performance (with measured benchmarks); architecture, security, privacy and data; product and docs; design (with screenshots and a mockup spec); and market research. Every high finding is re-checked at its source before the result is published as one private report page with verdicts, a Now/Next/Later plan, screenshots, mockups, and what was and was not verified. Run `/to-tickets` on the plan if you want issues.

### Removed

- `repo-audit`: **Breaking:** backlog reconciliation, epics, the ordered roadmap, the go-ahead step before GitHub changes, and the hand-off to `to-tickets`. The old skill is at the 3.1.0 release commit, `d95ab6f`.

## [3.1.0] - 2026-10-12

Slims both remaining skills: `council` drops its peer-rank round and `repo-audit` its cross-review round, roughly halving agents per run; `repo-audit` now asks before any GitHub change.

### Added

- ADR 0041: `/council` drops its peer-rank round, runs the lineup selector in the main session, and seats every panelist at one model tier; amends ADR 0036.

### Changed

- `council`: now runs a blind parallel panel and a single chair synthesis (about 4-6 agents per run instead of about 12). The chair reads every seat's output in shuffled order and still attributes the Rationale and Panel Dissent blocks to personas.
- `council`: the lineup is chosen in the main session by rule, with Security still force-seated on auth, payments, secrets, migrations and trust-boundary signals, and shown before any agents run; panels are 3-5 seats (0-2 conditional).
- `council`: seats run on sonnet and the chair on opus at high effort; the per-seat model tier is gone.
- `council`: scoped to design-level decisions; line-level defects belong to `/code-review`. Falls back to parallel Agent-tool calls when the Workflow tool is unavailable, and stops if neither is.
- `repo-audit`: the leverage hunt now runs at most six agents instead of eleven — the cross-review round is gone and a single synthesis agent drops any finding whose evidence it cannot confirm at the cited path, listing each drop; seats run on one model tier with schema-validated output.
- `repo-audit`: Stage 1 now builds an evidence pack for every seat — deterministic-detector digests and a git-history churn hotspot ranking — and seat selection skips lenses that do not apply and logs each skip.
- `repo-audit`: asks for your go-ahead, with the reconciliation and roadmap in front of you, before any issue is rewritten, closed, merged or created. The epic bodies it would publish are shown first.
- `repo-audit`: Stage 4 hands each epic to upstream `to-tickets` as a parent issue so tickets arrive as native sub-issues with native blocking links, and the audit ends with a copyable done-checklist.
- `repo-audit`: the Convention & Backlog lens no longer claims to see other lenses' findings; the synthesis agent detects supersession instead.

### Removed

- `council`: the "As a sub-skill" invocation (other skills cannot invoke a `disable-model-invocation` skill) and the peer-rank round.
- `repo-audit`: the anonymized cross-review round and its trace-stripping prose (recorded in an amendment to ADR 0041).
